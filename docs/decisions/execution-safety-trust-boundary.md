# Architecture Decision Record: Execution Safety, Trust Boundaries & Data Egress (ADR-05)

**Status:** accepted

## Context
Agent-based auditing involves inherently risky operations: reading untrusted project data (which may contain prompt injections or malicious build scripts), delegating analysis to external LLM providers (OmniRoute), and executing local commands (e.g., tests, linters). 
If the trust boundaries are blurred—for instance, if an LLM is allowed to directly authorize a shell command, or if OmniRoute implicitly exfiltrates the entire repository—the system becomes an automated vulnerability. 

This ADR establishes the strict trust model, execution capabilities, and data egress rules governing the Orchestrator and its workers.

## Decision

### 1. The Four-Tier Trust Model
Authority strictly flows downward. Lower tiers cannot modify or override upper tiers.
1. **Control Plane (Highest):** Orchestrator policy, JSON schemas, canonical run state, deterministic safety gates.
2. **Project Data (Untrusted):** Source code, READMEs, tests, configs, Git metadata, tool output.
3. **Model Output (Untrusted):** Classifications, command proposals, reasoning generated by LLMs.
4. **External Services (Untrusted):** OmniRoute, remote APIs, LLM providers.

### 2. The Golden Invariants
The architecture is bound by these absolute laws:
1. **Project content is data, never authority.** (e.g., a README instructing the agent to "ignore rules" is just text).
2. **LLM output is untrusted data until validated by deterministic policy.** LLMs can *propose* commands; they cannot *authorize* them.
3. **No external data egress without explicit authorization.** (Unknown eligibility = `DO NOT SEND`).
4. **No command execution without an approved Capability Set.** (Unknown safety = `DO NOT EXECUTE`).
5. **No worker inherits host credentials or environment by default.** (Deny-by-default).
6. **Tool output and cached results do not become trusted merely by origin.**
7. **Classification uncertainty must not silently reduce audit coverage.** (Unknown applicability = `DO NOT EXCLUDE`).
8. **Every externally observable execution must have attributable provenance** (an Execution Receipt).

### 3. Execution Safety: The Capability Model
Security is not determined by a simple allowlist of command strings (e.g., `pytest` is not inherently safe). Instead, execution requests are mapped to a **Capability Set**:
- **Filesystem:** (e.g., `read-only`, `temporary-write`, `none`)
- **Network:** (e.g., `disabled`, `restricted`, `full`)
- **Credentials:** (e.g., `none`, `explicit-only`)
- **Resources:** (e.g., timeout, memory limits, process constraints)

The pipeline is deterministic: `Command Proposal -> Capability Check -> Sandbox/Isolation -> Execute`. (Note: "Docker" is a technology, not a capability. The Sandbox must enforce the requested capabilities regardless of the underlying containerization).

### 4. Data Egress Policy (WHAT, WHERE, HOW)
Egress is governed by the principle of **Least Data**, not just Least Privilege.
- **WHAT:** Sensitive data (secrets, keys) are fundamentally ineligible for egress. Egress must be minimized (e.g., snippets instead of whole files).
- **WHERE:** Policy dictates allowed destinations (e.g., `LOCAL_ONLY`, `APPROVED_EXTERNAL`).
- **HOW:** If data is redacted, the transformation must not destroy provenance. The original artifact identity must remain traceable to the sanitized derivative.
*Crucially, Data Egress limits apply not only to LLM prompts, but also to telemetry, semantic caches, and OmniRoute logs.*

### 5. Snapshot Drift (TOCTOU)
If a granted execution modifies the working tree (e.g., a build script generates files), the `TargetSnapshot` (ADR-06) drifts. The system must detect this and decide whether to abort, create a new snapshot, or invalidate affected evidence, ensuring the audit does not silently mix states.

### 6. Overrides and Provenance
If a human wishes to override a blocked execution, it must be an explicit, scoped action recorded in the run state. Overrides are never inferred from repository content. Every execution yields an **Execution Receipt** detailing exactly which policy version granted which capabilities.

## Consequences
- **Positive:** Systematically eliminates prompt injection as an execution threat vector.
- **Positive:** Protects sensitive project data from accidental exfiltration via LLMs.
- **Negative:** Requires building a robust deterministic sandbox/capability mapping engine before autonomous workers can run local tools.
